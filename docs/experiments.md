# Retrieval experiments — LIC corpus (headline benchmark)

Reproduce with `policy experiments --set lic-real --k 5 --rerank --generate`. The block
below is regenerated by that command; everything outside it is written by hand and
survives a re-run.

**Corpus**: two real IRDAI-filed LIC policy wordings — *Digi Term* (UIN 512N356V02) and
*Jeevan Raksha* — 17 pages and 49 chunks each. The documents are not in the repository
(see `docs/sample-data.md`); `evals/questions-lic.yaml` carries the verified labels.

The synthetic suite still runs as a regression fixture and reports separately to
`docs/experiments-acme-synthetic-v2.md`. It is deliberately **not** mixed into these
numbers: a 4-page document we wrote ourselves would flatter them.

## Reading these numbers

- **Recall@k** and **MRR** are computed over answerable questions only; there is no evidence to retrieve for the rest.
- Evidence is matched by **page**, not chunk id, so these labels survive re-chunking. A chunk counts as a hit when its page range covers a labelled page.
- **Section acc.** is the stricter check: the right page for the right reason. A page can hold several clauses.
- Postgres full-text ranking is `ts_rank_cd`, **not BM25**. The `bm25` row is real BM25 (`rank_bm25`, in memory) so the comparison is measured rather than asserted.
- **Cond. coverage** applies to questions whose honest answer is conditional. They are excluded from the two rates above -- neither answering nor abstaining is wrong when the document holds several competing conditions -- and scored instead on whether *every* condition reached the model.
- Per-question output for every row is in `evals/results/`.

## Findings

### 1. The phase-2 verdict was corpus-bound, and it has been withdrawn

Phase 2 concluded that plain vector search beat every hybrid, and set the default
accordingly — while stating plainly that an 8-chunk synthetic corpus could not
generalise. It could not.

`hybrid RRF(vector + BM25)` reaches **Recall@5 = 1.000** here: every answerable
question's evidence retrieved, which vector alone (0.949) does not manage. Vector keeps a
narrow MRR lead, and the reranked hybrid takes the best MRR overall. The ordering of
strategies is simply different on a real corpus.

This is the result the phase-2 write-up was explicitly holding open, and it is the reason
that caveat was worth writing rather than burying.

### 2. Real BM25 beats `ts_rank_cd` by a margin that is not noise

| Arm | Recall@5 | MRR |
|---|---|---|
| `ts_rank_cd` | 0.872 | 0.608 |
| real BM25 | 0.974 | 0.795 |

An MRR gap of 0.187. On the synthetic corpus the same comparison gave 0.032 — inside the
noise floor, and reported as such.

The mechanism is IDF: BM25 weights rare terms, `ts_rank_cd` does not, and these documents
are dense with rare high-value tokens — `512N356V02`, `Section 45`, `Unexpired Risk
Premium Value`, `Panchnama`. The synthetic corpus had almost none of them, which is
exactly the gap phase 2 recorded as a limitation.

So the reversal condition written into `docs/decisions.md` has fired: **BM25 is worth real
infrastructure**, and the ParadeDB `pg_search` extension goes on the next phase's list.
Running BM25 as a measured experiment rather than asserting `ts_rank_cd` was adequate is
what made that decision available.

### 3. The winning configuration cannot ship as built

`hybrid RRF(vector + BM25)` uses the in-memory BM25 arm, which re-indexes the entire
scoped corpus on **every query**. That is a benchmark tool, and `rag/retrieval/bm25.py`
says so in its own docstring.

So the default stays `vector` for now. Switching it to the configuration that measured
best would trade a correctness win for a latency problem that grows with the corpus. The
honest order is `pg_search` first, re-measure, then change the default to a hybrid that is
actually deployable. Flipping a setting on the strength of a number produced by code that
cannot serve traffic would be the wrong lesson to take from a benchmark.

### 4. Section-aware retrieval was the top recommendation of the last phase, and it lost

Phase 2 ended by naming this "the first thing to try". It was built, measured, and
rejected:

| Configuration | Recall@5 | MRR |
|---|---|---|
| hybrid RRF(vector + `ts_rank_cd`) | 0.897 | 0.782 |
| + section arm | 0.923 | 0.772 |
| hybrid RRF(vector + BM25) | **1.000** | **0.898** |
| + section arm | 0.897 | 0.750 |

Added to the weaker pair it trades a little ranking for a little recall. Added to the best
pair it is destructive: 10 points of recall and 15 of MRR. The synthetic corpus agrees
(0.889 → 0.722 at k=1), so it is not a one-corpus artifact.

**Why it fails is more useful than the fact that it does.** A section path identifies a
*region*, not a *passage*. Eight chunks share `PART – D: CONDITIONS RELATED TO SERVICING
ASPECTS`; a query matching that path returns all eight at high rank, and each contributes
its reciprocal to the fusion. The arm floods RRF with weakly-relevant candidates and
dilutes the ones that matter. RRF treats every arm as an equal voter, and this signal is
not of equal quality.

The diagnosis behind it still stands — a term's definition really does outrank the clause
that governs it, and `section_path` really is the distinguishing signal. The remedy was
wrong. Section metadata belongs as a **tie-breaker within the fused list, or a filter when
a query names a section**, not as a fourth vote.

### 5. The chunker that passed every test was broken on real documents

Before this phase, section paths on these documents looked like:

```
 >  > PART- A
18. Endorsement means conditions attached/ affixed to this Policy incorporating any...
Name >  > DIVISIONAL OFFICE: BRANCH OFFICE:
```

Every chunking test passed. The synthetic fixture had headings in 16pt and 12.5pt against
10pt body text, so font prominence found them; in the LIC documents **564 body lines and
138 heading lines are all 10.0pt**, and bold is used for mid-sentence emphasis too.

Six fixes landed, each traced to an observed failure — see `docs/decisions.md`. The one
worth repeating is that a *benchmark question*, not a test, caught the worst of them: the
plan's UIN was absent from the corpus entirely, because it sits in the running header of
every page and furniture detection had deleted it rather than deduplicating it.

### 6. Cross-product attribution holds on near-identical documents

The two wordings are substantively near-identical — same 30-day grace period, same
five-year revival period, no surrender value, no maturity benefit, same 80% suicide
refund. That is the hardest case for the brief's "mixing clauses from different products"
risk, because the wording itself offers no signal about which document you are in.

Asked *"How is the sum assured on death calculated for a regular premium policy?"* scoped
to each policy in turn, the system cited the correct document both times and gave the two
genuinely different answers — Digi Term's *highest of three* including the absolute amount
assured, and Jeevan Raksha's *higher of two* floored at 105% of total premiums paid.

### 7. The abstention columns are not yet trustworthy, and the reason matters

The generation pass reports a **12% false-answer rate** for the two best-recall
configurations and 0% for the rest. Read naively that says the better retrieval is less
safe. It does not.

The 12% is **one question, flipped once, in one run**: `L043` — *"What rate of GST applies
to the premium?"* — out of 8 unanswerable questions. Re-run live under the same
configuration, it abstained 6 times out of 6, and under `vector` as well. `gpt-4o-mini` at
`temperature=0` is not deterministic, so a single flip moves this column by 12.5 points.

Two conclusions, kept separate because they have different standing:

- **The retrieval numbers are solid.** Recall@k, MRR, nDCG and conditional coverage are
  computed from embeddings and BM25 scoring, both deterministic. Run them twice and they
  do not move.
- **The generation numbers are not, at this sample size.** False-answer and
  false-abstention rates over 8 unanswerable and 38 answerable questions need repeated
  runs with a reported spread before any configuration can be called safer than another.
  The harness does single runs today. That is a gap in the measurement, not a property of
  the system, and it goes on the next phase's list.

What the question itself shows is still worth having. `L043` is a clause that *exists and
does not answer* — the tax section says taxes apply "as per the tax laws and the rate of
tax as applicable from time to time" and states no rate. The weaker configurations score
0% on false answers partly because they never retrieve that clause at all: **they are
right by accident**, and a 0% that comes from a retrieval miss is not a safety property.

### 8. Conditional coverage is the weakest number in the table, and one label is suspect

Conditional coverage runs 33–67%: of three conditional questions, one or two had *every*
labelled condition page reach the model.

`L040` — *"What should my family do to claim after my death?"* — fails in all eight
configurations. I labelled it pages 12 **and** 13, where 13 is the grievance-redressal
route if a claim is repudiated. Nothing retrieves page 13 for that question, and on
reflection the label is probably over-demanding rather than the retrieval being wrong: an
agent asking what documents to submit is not asking about repudiation appeals.

That is a labelling error of mine, not a system failure, and it is the kind that a metric
reported without inspection would have quietly hidden. It needs re-verifying against the
source before the next run, and it is a reminder that three conditional questions is too
few to carry a column.

## What this table still cannot tell you

The corpus is better than the last one by every measure that matters — 7x the chunks, real
distractors, real literal lookups, two products with near-identical wording — but it is
still **two documents from one insurer, both pure-risk term plans**.

Not yet exercised:

- **Other product classes.** No endowment, ULIP, annuity or health wording. Health
  policies are where the sub-limits and waiting-period tables live, and the table-handling
  work is largely unexercised here: these documents contain 2 tables across 17 pages.
- **Other insurers.** The `PART A..G` anchor is IRDAI-prescribed and should generalise
  across Indian insurers, but that is an expectation, not a measurement.
- **True version conflict.** Two different products, not two versions of one. Attribution
  across near-duplicates is tested; superseded-version behaviour is not.
- **Scanned documents.** Both extract cleanly, so OCR remains deliberately unbuilt.
- **Scale.** ~100 chunks. Still far from the point where the absence of an ANN index
  matters.
- **Repeated generation runs.** Findings 7 and 8 show the generation columns moving on
  single-question flips. Until the harness runs each configuration several times and
  reports a spread, treat false-answer and false-abstention rates as indicative only.
- **Enough conditional questions to support the column.** Three is not enough, and one of
  the three carries a label that needs re-verifying.
