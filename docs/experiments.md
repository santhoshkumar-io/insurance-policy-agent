# Retrieval experiments — LIC corpus (headline benchmark)

Reproduce with `policy experiments --set lic-real --k 5 --rerank --generate`. The block
below is regenerated by that command; everything outside it is written by hand and
survives a re-run.

**Corpus**: two real IRDAI-filed LIC policy wordings — *Digi Term* (UIN 512N356V02) and
*Jeevan Raksha* — 17 pages and 49 chunks each. The documents are not in the repository
(see `docs/sample-data.md`); `evals/questions-lic.yaml` carries the verified labels.

The synthetic suite still runs as a regression fixture and reports separately to
`docs/experiments-acme-synthetic-v2.md`. It is deliberately **not** mixed into these
numbers: a 4-page document we wrote ourselves would flatter them.

## Reading these numbers

- **Recall@k** and **MRR** are computed over answerable questions only; there is no evidence to retrieve for the rest.
- Evidence is matched by **page**, not chunk id, so these labels survive re-chunking. A chunk counts as a hit when its page range covers a labelled page.
- **Section acc.** is the stricter check: the right page for the right reason. A page can hold several clauses.
- Postgres full-text ranking is `ts_rank_cd`, **not BM25**. The `bm25` row is real BM25 (`rank_bm25`, in memory) so the comparison is measured rather than asserted.
- **Cond. coverage** applies to questions whose honest answer is conditional. They are excluded from the two rates above -- neither answering nor abstaining is wrong when the document holds several competing conditions -- and scored instead on whether *every* condition reached the model.
- Per-question output for every row is in `evals/results/`.

## Findings

### 1. The phase-2 verdict was corpus-bound, and it has been withdrawn

Phase 2 concluded that plain vector search beat every hybrid, and set the default
accordingly — while stating plainly that an 8-chunk synthetic corpus could not
generalise. It could not.

`hybrid RRF(vector + BM25)` reaches **Recall@5 = 1.000** here: every answerable
question's evidence retrieved, which vector alone (0.950) does not manage. Vector keeps a
narrow MRR lead, and the reranked hybrid takes the best MRR overall. The ordering of
strategies is simply different on a real corpus.

This is the result the phase-2 write-up was explicitly holding open, and it is the reason
that caveat was worth writing rather than burying.

### 2. Real BM25 beats `ts_rank_cd` by a margin that is not noise

| Arm | Recall@5 | MRR |
|---|---|---|
| `ts_rank_cd` | 0.850 | 0.593 |
| real BM25 | 0.975 | 0.781 |

An MRR gap of 0.188. On the synthetic corpus the same comparison gave 0.032 — inside the
noise floor, and reported as such.

The mechanism is IDF: BM25 weights rare terms, `ts_rank_cd` does not, and these documents
are dense with rare high-value tokens — `512N356V02`, `Section 45`, `Unexpired Risk
Premium Value`, `Panchnama`. The synthetic corpus had almost none of them, which is
exactly the gap phase 2 recorded as a limitation.

So the reversal condition written into `docs/decisions.md` has fired: **BM25 is worth real
infrastructure**. Running BM25 as a measured experiment rather than asserting `ts_rank_cd`
was adequate is what made that decision available.

What that infrastructure turned out to be is not what this finding originally predicted —
see finding 3.

### 3. The winning configuration could not ship, so it was made shippable

The previous version of this section ended here: *"the default stays `vector`… the honest
order is `pg_search` first, re-measure, then change the default."* The BM25 arm re-indexed
the entire scoped corpus on **every query** — a benchmark tool, as `rag/retrieval/bm25.py`
said in its own docstring — so the configuration that measured best could not serve
traffic, and flipping a setting on its strength would have been the wrong lesson to take
from a benchmark.

**`pg_search` turned out to be the wrong answer**, for a reason that has nothing to do with
retrieval quality: the deployment target is managed Postgres, and neither Neon nor Supabase
offers the extension. Adopting it would have forced self-hosting to win a benchmark row.

So the index is built once per `(tenant, policy scope)` and cached instead:

| | |
|---|---|
| index build | 10 ms, one-off per scope |
| cold query (build + score + fetch) | 67.8 ms |
| warm query p50 | **4.9 ms** |
| speedup | **13.7x** |

Invalidation is a fingerprint query — `count`, `max(created_at)`, `max(ordinal)` over the
scope — not an `invalidate()` hook from the ingestion pipeline. A hook is simpler and
wrong: ingestion runs in a background task and, deployed, possibly in another process, so
it would leave every other worker serving a stale index with no way to notice. The tenant
is part of the cache key, which is the one mistake in this design that would be a security
bug rather than a performance one, and it is the first assertion in
`tests/test_bm25_cache.py`.

**The default is now `hybrid_bm25`**, chosen on recall rather than MRR: the model is handed
every one of the `top_k` chunks, so evidence that never arrives cannot be recovered by any
later stage, while imperfect ordering inside that set is a soft cost. Reranking has the
best MRR (0.921) and costs 5 points of recall for 10x the latency, so it stays off.

What it costs, stated rather than glossed: each worker holds its own index, so memory and
cold-start multiply by worker count; the first query after an ingest pays the rebuild; and
this is sound at ~100 chunks and needs revisiting well before ~10⁵, at which point
`pg_search` on self-hosted Postgres becomes the answer and arrives as another arm rather
than a rewrite.

### 4. Section-aware retrieval was the top recommendation of the last phase, and it lost

Phase 2 ended by naming this "the first thing to try". It was built, measured, and
rejected:

| Configuration | Recall@5 | MRR |
|---|---|---|
| hybrid RRF(vector + `ts_rank_cd`) | 0.897 | 0.782 |
| + section arm | 0.923 | 0.772 |
| hybrid RRF(vector + BM25) | **1.000** | **0.898** |
| + section arm | 0.897 | 0.750 |

Added to the weaker pair it trades a little ranking for a little recall. Added to the best
pair it is destructive: 10 points of recall and 15 of MRR. The synthetic corpus agrees
(0.889 → 0.722 at k=1), so it is not a one-corpus artifact.

**Why it fails is more useful than the fact that it does.** A section path identifies a
*region*, not a *passage*. Eight chunks share `PART – D: CONDITIONS RELATED TO SERVICING
ASPECTS`; a query matching that path returns all eight at high rank, and each contributes
its reciprocal to the fusion. The arm floods RRF with weakly-relevant candidates and
dilutes the ones that matter. RRF treats every arm as an equal voter, and this signal is
not of equal quality.

The diagnosis behind it still stands — a term's definition really does outrank the clause
that governs it, and `section_path` really is the distinguishing signal. The remedy was
wrong. Section metadata belongs as a **tie-breaker within the fused list, or a filter when
a query names a section**, not as a fourth vote.

**So it was rebuilt as a tie-breaker, and it lost again.** `apply_tiebreak` reorders
results whose fused scores sit within a relative tolerance of one another and **never adds
or drops a candidate** — the contract the arm version broke. A tolerance sweep on the
corrected labels says there is no setting where it pays:

| Tolerance | Recall@5 | MRR |
|---|---|---|
| off | 1.000 | **0.884** |
| 0.01 | 1.000 | 0.884 |
| 0.02 | 1.000 | 0.884 |
| 0.05 | 1.000 | 0.841 |
| 0.15 | 1.000 | 0.746 |

Monotonically harmful: narrow enough to be safe is narrow enough to do nothing, and wide
enough to act is wide enough to hurt. The sweep exists to rule out a mis-tuned parameter
before concluding, because "it lost" and "I set it badly" are not the same claim.

The root cause is identical in both shapes. A section path names a *region*, so it cannot
distinguish "this chunk is in the right section" from "this chunk is the right passage" —
and ranking needs the second. Two mechanisms, one failure.

**Stopping here.** The remaining variant is a hard *filter* when a query unambiguously
names a section. It is a different mechanism and might work, but two attempts have failed
for one shared reason, and a third would be persistence rather than evidence. Recorded as
a dead end for ranking; the filter is noted as untested, not promised. For the record the
original failure is now largely moot: at Recall@5 = 1.000 the definition-above-clause
ordering no longer costs a correct answer.

### 5. The chunker that passed every test was broken on real documents

Before this phase, section paths on these documents looked like:

```
 >  > PART- A
18. Endorsement means conditions attached/ affixed to this Policy incorporating any...
Name >  > DIVISIONAL OFFICE: BRANCH OFFICE:
```

Every chunking test passed. The synthetic fixture had headings in 16pt and 12.5pt against
10pt body text, so font prominence found them; in the LIC documents **564 body lines and
138 heading lines are all 10.0pt**, and bold is used for mid-sentence emphasis too.

Six fixes landed, each traced to an observed failure — see `docs/decisions.md`. The one
worth repeating is that a *benchmark question*, not a test, caught the worst of them: the
plan's UIN was absent from the corpus entirely, because it sits in the running header of
every page and furniture detection had deleted it rather than deduplicating it.

### 6. Cross-product attribution holds on near-identical documents

The two wordings are substantively near-identical — same 30-day grace period, same
five-year revival period, no surrender value, no maturity benefit, same 80% suicide
refund. That is the hardest case for the brief's "mixing clauses from different products"
risk, because the wording itself offers no signal about which document you are in.

Asked *"How is the sum assured on death calculated for a regular premium policy?"* scoped
to each policy in turn, the system cited the correct document both times and gave the two
genuinely different answers — Digi Term's *highest of three* including the absolute amount
assured, and Jeevan Raksha's *higher of two* floored at 105% of total premiums paid.

### 7. I called a result noise, and I was wrong — it was my label

**Correction to the previous version of this document.** The generation pass reported a
12% false-answer rate for the two best-recall configurations. I investigated, found the
single responsible question abstaining 6 times out of 6 on re-test, and concluded the
result was run-to-run noise from a non-deterministic model.

That conclusion did not survive. On a later repeated measurement the same question
answered **8 times out of 8** — the opposite result, which no single stable distribution
explains. The cached BM25 index had landed in between, so it was the obvious suspect; a
bit-for-bit equivalence check against the uncached implementation showed identical
rankings and identical scores, clearing it. (That check is now
`test_the_cached_index_scores_identically_to_a_fresh_one`, written because it was needed
rather than because it was planned.)

Reading **what the system actually said** settled it:

> "The amount of applicable taxes as per the prevailing rates shall be payable by the
> policyholder on premiums..."

Asked *"What rate of GST applies to the premium?"*, it quoted the tax clause and **did not
invent a rate**. That is the behaviour this whole project is built to produce. The label
was marking it a failure.

The document genuinely answers *"what does this policy say about tax"* and genuinely does
not answer *"what rate"*. A binary flag cannot express **"topic present, value absent"**,
any more than it could express "depends on facts not supplied" — the gap that produced the
`conditional` state. So `L043` was rewritten to ask what the document can answer, and the
original trap was preserved as `L048` with a note telling the reader to check the
per-question output before trusting its score.

Three things worth taking from this:

- **Metrics route attention; they do not conclude anything.** Every real finding in this
  phase came from reading the per-question output, not the table.
- **"It's noise" is a conclusion that needs evidence too.** Six observations felt like
  enough. It was the wrong six.
- **The generation columns remain weak at this sample size** — 8 unanswerable questions
  means one flip moves the rate 12.5 points. Retrieval metrics are deterministic and
  stand; generation metrics need repeated runs with a reported spread, which the harness
  does not do yet.

**Measured afterwards, rather than argued about:** `L048` was run 10 times against a fixed
retrieved set. It answered **5 times and abstained 5** — a genuine coin flip, which is why
one run reports a 12% false-answer rate and the next reports 0%. And when it answers, it
quotes the statutory-taxes clause and **still does not invent a rate**. So the single
"false answer" in this table is one borderline question flipping, not a fabrication. The
rate is real as a number and misleading as a summary, which is the whole reason the
per-question output is published alongside it.

### 8. Conditional coverage was measuring my labelling, not the system

Conditional coverage ran 33–67%, and `L040` — *"What should my family do to claim after my
death?"* — failed in all eight configurations.

It was labelled pages 12 **and** 13, where 13 is the grievance route if a claim is
repudiated. Nothing retrieves page 13 for that question, and nothing should: an agent
asking which documents to submit is not asking about appeals. The label was wrong.

Dropping page 13 then made it conditional with a single page, which the loader **rejects** —
correctly, because with one page it is an ordinary answerable question. Its answer really
is conditional on cause of death, but both conditions sit on the same page, and coverage
is page-based, so the metric cannot see the distinction.

That is a limitation of the metric, not of the question, so the question is now plainly
answerable and the limitation is recorded rather than hidden behind a label that happened
to fit the schema. Two conditional questions remain, which is too few to carry a column —
stated here rather than reported as a percentage.

### 9. Retrieval is finished; every remaining error is in generation

This is the finding that decides what to do next, and the table does not show it.

At the default configuration, the five questions scored as **false abstentions** — the
system declining to answer something the document answers — all have `recall = 1.0`. Three
of the five had the evidence at **rank 1**. The text was retrieved, served to the model,
and the model declined.

Three were verified by reading the wording rather than trusting the label:

| Question | What the document says | What the system said |
|---|---|---|
| `L023` Can I take a loan against this policy? | "No loan will be available under this policy" (p. 9, last sentence of the surrender section) | "The sources do not provide any information regarding the ability to take a loan" |
| `L015` Can the death benefit option be changed after issue? | "The Death Benefit Option once chosen cannot be changed later" (p. 7) | "The sources do not provide information regarding whether the death benefit option can be changed" |
| `L025` Does the suicide clause apply to a lapsed policy? | "This clause shall not be applicable for a lapsed policy as nothing is payable under such policies" (p. 11) | *"The sources indicate that the suicide clause does not apply to lapsed policies, but they do not provide details…"* — and then abstained |

`L025` is the sharpest of the three: the abstention reason **states the answer** and
declines anyway. `L023` and `L015` were each run 10 times and abstained **10 out of 10**,
so this is not sampling variance; it is a reproducible behaviour.

Two mechanisms are visible. A single decisive sentence at the end of a long formula-heavy
chunk gets overlooked — `L023`'s answer is the last line of a surrender-value calculation.
And the model treats **"not elaborated" as "not stated"**, which is over-abstention
wearing the costume of caution.

That matters because abstention is a feature of this system, and a feature that fires when
it should not is a defect with good manners. It also redirects the next phase: at
Recall@5 = 1.000 there is nothing left to win in retrieval, and the honest target is the
answerability judgement in `rag/generation/`.

### 10. What the measurement cost, and what it bought

Three retrieval ideas were built and measured this phase and the previous one. Two were
rejected: section metadata as an RRF arm, and the same signal as a tie-breaker. One was
adopted after being made deployable. The reranker was measured and left off.

The table rows for the rejected ideas are the cheapest part of this document to delete and
the most expensive to re-derive, which is why they stay.

## What this table still cannot tell you

The corpus is better than the last one by every measure that matters — 7x the chunks, real
distractors, real literal lookups, two products with near-identical wording — but it is
still **two documents from one insurer, both pure-risk term plans**.

Not yet exercised:

- **Other product classes.** No endowment, ULIP, annuity or health wording. Health
  policies are where the sub-limits and waiting-period tables live, and the table-handling
  work is largely unexercised here: these documents contain 2 tables across 17 pages.
- **Other insurers.** The `PART A..G` anchor is IRDAI-prescribed and should generalise
  across Indian insurers, but that is an expectation, not a measurement.
- **True version conflict.** Two different products, not two versions of one. Attribution
  across near-duplicates is tested; superseded-version behaviour is not.
- **Scanned documents.** Both extract cleanly, so OCR remains deliberately unbuilt.
- **Scale.** ~100 chunks. Still far from the point where the absence of an ANN index
  matters.
- **Repeated generation runs.** Findings 7 and 9 show the generation columns moving on
  single-question flips — and, where it was measured by hand, one question flipping 5/5
  out of 10. The harness still runs each configuration once, so treat the false-answer and
  false-abstention columns as indicative and read the per-question output. Adding
  `--repeats` with a reported spread is the first thing the harness needs.
- **Enough conditional questions to support the column.** Two is not enough to report as a
  percentage, which is why finding 8 states it in words instead.
